# Requirements: Observator Clew

Hand-written before the event as a planning document. Not generated by Kiro. Declared in the README as prepared-before work, alongside the other planning docs. The code that satisfies these requirements is built during the event.

Scope is closed. These ten requirements are the entire build. See the Scope gate in `planning/ARCHITECTURE.md`.

---

## Requirement 1: Deterministic triage

**User story:** As someone with 62 repositories, I want a deterministic layer to decide which repos are even worth a closer look, so that the model's judgment is spent on candidates rather than on everything.

**Acceptance criteria:**
1. WHEN the system loads the estate snapshot THE SYSTEM SHALL assign every repository exactly one bucket and a one-line deterministic reason.
2. WHEN triage completes THE SYSTEM SHALL produce bucket counts that sum to the total repository count.
3. THE SYSTEM SHALL use descriptive bucket names only, assigned by age and mutually exclusive: insufficient-evidence (pushed_at missing), recently-active (90 days or fewer), quiet (91 to 365 days), long-quiet (over 365 days).
4. THE SYSTEM SHALL NOT use bucket names that imply a verdict, such as archive-candidate or abandoned.
5. THE SYSTEM SHALL carry has_deployment_evidence as an orthogonal boolean per repository, NOT as a bucket. The signal worth surfacing is quiet combined with deployment evidence, and that pairing is lost if deployment is its own bucket.
6. THE SYSTEM SHALL measure repository age against the snapshot's capture date, not wall-clock time, so results are reproducible.
5. WHEN triage runs THE SYSTEM SHALL make no model calls.

## Requirement 2: Agent-directed investigation

**User story:** As the owner of the estate, I want the agent to decide what evidence it needs and read it, so that its judgment rests on what a repository actually contains rather than on metadata alone.

**Acceptance criteria:**
1. WHEN given candidates THE SYSTEM SHALL allow the model to request specific files via a `fetch_file` tool.
2. WHEN the model requests a file THE SYSTEM SHALL execute a live GitHub API fetch and return the real contents to the model.
3. WHEN the model receives file contents THE SYSTEM SHALL allow it to judge only after seeing them.
4. THE SYSTEM SHALL bound the loop at MAX_TOOL_TURNS = 4 per run, enforced in code.
5. WHEN a GitHub fetch fails THE SYSTEM SHALL fall back to snapshot data AND label the fallback in the output.
6. THE SYSTEM SHALL NOT pre-fetch all evidence into a single model call.
7. THE SYSTEM SHALL treat fetched file contents as untrusted data, never as instructions.

## Requirement 3: Structured, explainable findings

**User story:** As someone deciding whether to act, I want every finding to show its reasoning and its limits, so that I can tell what is established from what is inferred.

**Acceptance criteria:**
1. WHEN the model produces a finding THE SYSTEM SHALL validate it against the Pydantic schema in `prompts/output_schema.md`.
2. THE SYSTEM SHALL require why_surfaced, what_checked, what_found, what_cant_know, recommendation, and recommendation_reason on every finding.
3. THE SYSTEM SHALL require recommendation_reason for SUPPRESS as well as SURFACE.
4. WHEN a finding cites a repository name not present in the snapshot THE SYSTEM SHALL reject the response and retry once.
5. WHEN what_cant_know is empty or a placeholder THE SYSTEM SHALL reject the response and retry once.
6. WHEN a retry also fails validation THE SYSTEM SHALL drop that finding and log it, without crashing the run.
7. THE SYSTEM SHALL NOT allow the model to restate facts differently from the snapshot.

## Requirement 4: Policy guard

**User story:** As the person being interrupted, I want code rather than the model to decide whether something actually reaches me, so that the interruption threshold is auditable.

**Acceptance criteria:**
1. WHEN the model recommends SURFACE THE SYSTEM SHALL apply a deterministic policy check before any message is sent.
2. THE SYSTEM SHALL keep the policy guard in code the model cannot reach or influence.

## Requirement 5: Unprompted Telegram briefing

**User story:** As someone who will not remember to ask, I want the briefing to arrive without me requesting it.

**Acceptance criteria:**
1. WHEN the application starts THE SYSTEM SHALL send a briefing via job_queue without any user command.
2. THE SYSTEM SHALL send with parse_mode HTML and escape `<`, `>`, and `&` in interpolated text.
3. THE SYSTEM SHALL assert message length is under 4096 characters before sending.
4. THE SYSTEM SHALL cap the briefing at the top three surfaced findings.
5. THE SYSTEM SHALL include the funnel header: observed, signaled, investigated, surfaced.
6. THE SYSTEM SHALL include the Estate Overview link from ESTATE_OVERVIEW_URL.

## Requirement 6: Decision capture

**User story:** As the person reading the briefing, I want to tell the agent what I decided directly in the message, so that the decision is recorded where I made it.

**Acceptance criteria:**
1. THE SYSTEM SHALL attach Investigate and No action inline buttons to each surfaced finding.
2. THE SYSTEM SHALL assert callback_data is under 64 bytes before building the keyboard.
3. THE SYSTEM SHALL encode short identifiers in callback_data, never raw repository names.
4. WHEN a button is tapped THE SYSTEM SHALL call query.answer() as the first action in the handler.
5. WHEN a decision is recorded THE SYSTEM SHALL write repo, decision, decided_at, and an evidence_fingerprint of pushed_at, archived, open_issues_count, and the sorted deploy-file set to `state/decisions.json`.

## Requirement 7: Persistence guard

**User story:** As someone who already said no once, I want that decision respected until the evidence changes, so that the agent stops bringing it up.

**Acceptance criteria:**
1. WHEN a run begins THE SYSTEM SHALL read `state/decisions.json` BEFORE calling the model.
2. WHEN a candidate has a stored no_action decision AND its recomputed evidence fingerprint is unchanged THE SYSTEM SHALL skip that candidate entirely and make no model call for it.
3. WHEN a candidate is auto-suppressed THE SYSTEM SHALL count it as suppressed and include a one-line note citing the stored decision and date.
4. WHEN the evidence fingerprint has changed THE SYSTEM SHALL send the candidate to the model as normal.
5. THE SYSTEM SHALL key suppression on repo plus evidence fingerprint, never on finding text.

## Requirement 8: Estate Overview

**User story:** As someone who wants to check a claim, I want a page showing the full reasoning for every finding, so that the Telegram summary is not the only record.

**Acceptance criteria:**
1. WHEN a run completes THE SYSTEM SHALL render real data into `docs/index.html`.
2. THE SYSTEM SHALL render at run end only, never on a button tap.
3. THE SYSTEM SHALL preserve the existing palette tokens, layout, four-part grammar, and funnel strip.
4. THE SYSTEM SHALL NOT add JavaScript, external assets, or CDN references.

## Requirement 9: Replay

**User story:** As someone demonstrating this live, I want to resend a known-good result, so that a network failure during recording does not end the demo.

**Acceptance criteria:**
1. WHEN a run completes THE SYSTEM SHALL write the result to `runs/latest.json`.
2. WHEN invoked with --replay THE SYSTEM SHALL send the saved result without calling the model or GitHub.
3. THE SYSTEM SHALL construct the OpenAI client with timeout=20 so that a stalled connection fails fast rather than hanging.

## Requirement 10: Honest disclosure

**User story:** As a judge, I want to see exactly what was built during the event, so that I can evaluate the work accurately.

**Acceptance criteria:**
1. THE SYSTEM SHALL maintain a README section listing what existed before the event.
2. WHEN the build completes THE SYSTEM SHALL have a README section listing what was built during the event.
3. THE SYSTEM SHALL NOT describe inherited work as event work.
4. THE SYSTEM SHALL NOT commit `.env` or expose credentials in code, logs, or output.
